# 🔗 연결고리 (LINK)

> 흩어진 소액 사기 피해를 하나의 고액 사기 사건으로 묶는다.
> "혼자 신고하면 45만 원, 묶으면 약 2,100만 원짜리 사건입니다."

같은 사기범에게 당한 중고거래 사기 피해자들을 **신원을 드러내지 않고 찾아 모으고**, 피해자들의 **봉인된 증거를 대표 피해자 한 명에게 모아주는** 모바일 웹 서비스입니다. 서버는 사기범 단서(계좌번호 등)의 원래 값을 저장하지 않고, 증거는 암호화해서 보관합니다. 경찰 제출은 대표 피해자가 직접 합니다.

## 실행 방법

```bash
npm install
cp .env.example .env.local   # CLUE_PEPPER=link-demo-pepper-2026 처럼 값 입력 (서버 전용 키)
npm run dev                  # http://localhost:3000
npm run test:security        # 보안 테스트 (8개)
```

- DB 없음: 서버 메모리에 저장하고, 서버를 재시작하면 시드 데이터(피해자 A~D)가 다시 만들어집니다.
- 로그인 없음: 상단 드롭다운으로 데모 유저 A/B/C/D를 전환합니다(쿠키).
- 모바일 화면 폭 390px을 기준으로 만들었습니다.
- 예전 키 이름(`NEXT_PUBLIC_CLUE_PEPPER`)도 서버에서만 읽어 그대로 동작합니다. 새로 만들 때는 `CLUE_PEPPER`를 쓰세요.

## 데모 시나리오

1. `/debug`: 서버 저장소에서 `110123456789`를 검색하면 **0건**입니다. 단서는 해시로만 저장되고, 증거는 `enc:v1:…` 암호문으로만 보입니다.
2. 유저 A의 홈에서는 A·B·C가 한 그룹으로 묶여 **합산 135만 원**이 나옵니다. 유저 D는 `매칭 대기 중`입니다.
   - A `110-123-456789` ↔ B `110123456789` (하이픈 차이)
   - B `https://safe-pay-check.com/order` ↔ C `www.safe-pay-check.com` (프로토콜·www·경로 차이)
3. A가 `제가 대표할게요`를 누른 뒤 B와 C로 전환해 각각 `대표 승인하기`를 누릅니다. 그러면 `대표 확정`이 됩니다.
4. B와 C가 `증거 위임하기`에서 "대표가 내 이름과 증거를 보게 됩니다" 안내를 확인하고, 이름을 입력해 동의합니다.
5. A로 전환해 `증거 묶음 보기`를 엽니다. 맨 위에 착수금·수수료 경고가 있고, 사건 요약, 타임라인, 피해자별 증거가 보이며 모든 증거가 `변경 없음 ✓`입니다.
   - B가 같은 주소(`/api/groups/:id/bundle`)를 요청하면 **403** (`대표만 볼 수 있어요`)이 반환됩니다.

## 동작 원리

| 단계 | 내용 |
|---|---|
| 단서 정규화 | 계좌·전화는 숫자만 남기고(`+82`·`82`는 `0`으로), 닉네임·카톡 ID는 소문자로 바꾸고 공백과 앞의 `@`를 없앱니다. URL은 프로토콜·`www.`·경로·포트를 떼고 도메인만 남깁니다. (`lib/normalize.ts`) |
| 해시 | 서버만 가진 키로 `HMAC-SHA256(pepper, "type:value")`를 계산합니다(`/api/clue-hash`). 키는 브라우저 번들에 들어가지 않고, 원문은 저장·로그하지 않습니다. |
| 그룹화 | 서버는 해시가 하나라도 겹치는 피해 건을 Union-Find로 묶습니다(등록할 때마다 전체를 다시 계산). |
| 익명성 | API 응답에는 다른 피해자의 금액·단서·이름이 들어가지 않고, `피해자 A · 11월 3일` 같은 카드만 보입니다. **합산 피해액은 3명 이상일 때만** 보여줍니다(2명이면 상대 금액이 역산되므로). 대표 화면의 위임자 이름만 예외입니다. |
| 봉인 | 업로드할 때 브라우저가 SHA-256을 계산해 보내면, **서버가 받은 파일로 다시 계산해 대조**하고 다르면 거부합니다. 봉인 시각은 서버 시각입니다. 대표 화면에서 해시를 다시 계산해 비교합니다. |
| 저장 암호화 | 증거 파일은 서버에 **AES-256-GCM 암호문**으로 저장합니다(`lib/evidence-crypto.server.ts`). 본인 증거 조회와 대표 화면 응답에서만 복호화합니다. 암호문이 조금만 바뀌어도 복호화가 실패합니다. |
| 접근 제어 | 그룹 정보는 구성원만, 증거 묶음은 확정된 대표만 볼 수 있습니다. 증거는 위임에 동의한 사람 것만 대표에게 갑니다. 남의 피해 건에는 증거를 올릴 수 없고, 이미지가 아니거나 5MB를 넘는 파일은 거부합니다. (`lib/access.ts`) |

### 왜 일반 해시가 아니라 HMAC인가

계좌·전화번호는 경우의 수가 적어서 SHA-256만 쓰면 가능한 값을 전부 대입해 원문을 복원할 수 있습니다. 비밀키가 있어야 계산되는 HMAC을 쓰고, 그 키를 서버에만 두어 DB만 유출돼서는 역추적이 안 되게 했습니다. 단서 종류(`type`)를 함께 넣어 계좌와 전화가 우연히 같은 숫자여도 다른 해시가 나옵니다.

## 보안 검증

`npm run test:security`와 실행 중인 서버로 확인했습니다.

| 항목 | 결과 |
|---|---|
| `110-123-456789` / `110 123 456789` → 같은 해시 | ✅ |
| 다른 계좌, 같은 숫자의 다른 단서 종류 → 다른 해시 | ✅ |
| `010-…` / `+82 10-…` / `82…` → 같은 값 | ✅ |
| `https://www…/order` / 대문자 / 포트 / 경로 → 같은 도메인 | ✅ |
| 카톡 ID `@Seller_Kim` / `seller_kim` → 같은 값 | ✅ |
| 증거 1바이트 변경 → 해시 달라짐 | ✅ |
| 가짜 해시로 증거 업로드 → 400 거부 | ✅ |
| `/debug` 증거 → `enc:v1:…` 암호문만 보임, 계좌번호 검색 0건 | ✅ |
| 대표가 아닌 구성원의 번들 요청 → 403 | ✅ |
| 합산 공개: 2명 숨김, 3명 135만 원 | ✅ |
| 빌드 결과(브라우저 번들)에 HMAC 키 없음 | ✅ |

## 알려진 한계

- **해시 계산 순간 원문이 서버를 지나갑니다.** 키는 서버에만 있고 원문은 저장하지 않지만, 운영자는 마음먹으면 대입 공격을 할 수 있습니다. 실서비스에서는 **OPRF(서버 보조 블라인드 해시)** 또는 **PSI(비공개 교집합)**로 바꿔 서버도 원문을 모르게 해야 합니다.
- **증거 암호화 키도 서버에 있습니다.** DB 유출에는 안전하지만 운영자는 원칙적으로 복호화할 수 있습니다. 실서비스에서는 증거를 AES-GCM으로 암호화하고 그 키를 **대표 공개키(RSA-OAEP)**로 감싸는 증거 봉투로 바꿔야 합니다.
- 봉인은 업로드 이후의 변조를 잡아내지만, 업로드 전에 조작된 파일까지 막지는 못합니다.
- 대표는 위임한 사람의 이름과 증거를 볼 수 있습니다(위임 화면에서 미리 안내).
- 로그인·본인인증, DB, 경찰 제출 연동, 알림, 악용 대응은 범위 밖입니다. 메모 등 자유 입력이 생기면 연락처·계좌를 가리는 `maskPersonalInfo`를 적용합니다.
